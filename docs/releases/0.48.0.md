# Arugula 0.48.0

Agents drive Cloud workspaces (#1094). An agent on a machine joined to
control can list, read and drive its owner's Cloud workspaces through the
`arugula` MCP server, the way it drives panes.

## Cloud workspaces over MCP

- **`list`** gains `cloud_workspaces`, `cloud_tabs` (a workspace's tabs)
  and `cloud_agents` (what a tab can be opened with).
- **`read_cloud`** reads a tab's `events` and `requests`, and a
  workspace's `files`, `file`, `diff`, `git_status` and `setup_log`.
- **`cloud`** acts: `create` a workspace, `open_tab`, `prompt` (which
  waits for the turn and returns the reply, like `prompt_agent`),
  `interrupt`, `answer` a request, `close_tab`, `rebuild` and `retry`.
- **`wait`** takes `cloud_workspace` and `tab`, until `idle` or
  `needs_input`.
- **`capabilities`** says under `control.cloud` whether Cloud workspaces
  can be reached from here.
- Results carry a `link` to the workspace on control's page. There is no
  `show` kind for one yet.
- **Who can:** any agent on the machine, acting as the machine owner's
  account. A teammate with run rights on your machine can drive your Cloud
  workspaces through the agents there. Changing a workspace's settings,
  deleting it, cancelling a rebuild, secrets, the agent library and past
  tabs stay a person's.

## For whoever runs control

- Control takes a daemon's signature on the Cloud workspace and tab
  routes, scoped to the account on its certificate. Deploy control for the
  tools to work; a daemon on 0.48.0 against an older control is refused.
- `docs/mcp-permissions.json` and `arugula hooks install` allow
  `read_cloud`; `cloud` asks first.
