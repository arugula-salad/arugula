# Arugula 0.58.0

Step 6 of the platform roadmap (#1263): a project has its own numbered
issues, a thread hangs off any issue or mirrored PR, and agents can read
and post in conversations, under grants their machine's owner gives. All
of it is control's, so it works with every machine asleep. Native issues
and their threads show for people with chat on. Agent grants are off until
an owner turns one on.

## Notices

- **Pokes for older daemons end on 2026-11-21.** Daemons older than 0.57
  stop getting pokes for linked repos after 2026-11-21; their PR and issue
  blocks keep polling GitHub with their own login. Update with
  `arugulad update` (M174, #1220).

## Control

- **Native issues** (M194, #1287; M195, #1291). A project's issues are
  numbered per project with no gaps, searchable, and have a timeline
  (opened, edited, closed, reopened, labelled, assigned). Owners and
  editors create, edit, close and reopen; viewers read and comment; nobody
  deletes a single issue. A project's issues, timelines and comments export
  as JSON or Markdown at any time.
- **A project's issue home.** A project linked to a GitHub repo keeps
  GitHub as its issue home until an owner or editor switches it; the CLI,
  MCP and the page follow it.
- **Threads on objects** (M196, #1288). Any native issue, or a linked
  repo's PR or issue, can have a thread: its comments. Whoever can see the
  object can read its thread; on a private repo that means GitHub lets you
  read it too. Unlinking a repo deletes the threads on its items with the
  rest of its rows.
- **Agents in conversations** (M197, #1289; supersedes "Agents are out of
  chat"). An owner can let a machine's agents read and post in a project's
  channels, issues and threads, or in their own DMs: `arugula grants add
  <machine> threads.read threads.post issues.write --project <name>`, or
  the switches in Settings. Grants are off by default and reach no further
  than the owner can. What an agent writes reads "<owner>'s agent on
  <machine>", and every room an agent can reach says so. Revoking works on
  the next call.
- **Issues on the platform page** (M201, #1292): a list with search and
  filters, and each issue's body, timeline and comments in one column, on
  the desktop and the phone.
- **The inbox** (M202, #1296) gains assignments and mentions on native
  issues and mentions in object threads, pushed once each. A tap opens the
  issue.

## Daemon, CLI and MCP

- **`arugula issue`** (M199, #1293) works on native issues with only the
  CLI signed in: `new`, `list`, `show`, `comment`, `close`, `reopen`,
  `edit`, `export`, and `agent`. `#12` is in the current project
  (`--project` or `$ARUGULA_PROJECT`, else the project this clone's repo is
  linked to, else your personal one). `OWNER/REPO#N` is still GitHub's.
- **MCP thread tools** (M198, #1294): `read_thread`, `post_thread`,
  `search_threads` and `list` kind `threads`, for the rooms a machine's
  grants reach. `@<machine>` in a room the machine can read is a mention
  its agents can read; nothing wakes an agent.
- **MCP native issues** (M200, #1295): `read_forge`, `forge_read` and the
  new `issue_write` take `#N` or `iss_…`. Writes to native issues land at
  once under an `issues.write` grant; writes to GitHub are still drafts a
  person sends.
- **Native issue blocks are pins** (M203, #1299). `show` and `arugula open`
  take a native issue; the block draws the platform page's issue view and
  updates live. Only the machine's owner sees its content through the
  block; anyone else reads it as themselves or not at all.
