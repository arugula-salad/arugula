# Arugula 0.54.0

Step 2 of the platform roadmap, first half (#1150): control is split into
a hub and a platform inside one process, ready to run as two. Nothing on
screen changes, and the hosted control still runs the platform in process;
the switch to two processes is a short announced window after this
release.

## Control

- **Two processes, one address** (aru-075–078). The hub keeps sign-in,
  devices, rosters, the relay, push, Shared Docs, the ssh jump host, forge
  and telemetry. The platform (`crates/platform`) holds chat, Cloud,
  billing, projects and grants, and reaches the hub only through one
  interface, `HubPort`. Every path stays on control's address: the hub
  becomes a gateway in front of the platform, so daemons and apps of any
  version keep working.
- **`arugula-platform`**, a binary that runs the platform as its own
  process behind the hub's gateway, on the private network only. Control
  keeps an in-process mode (the default, and the rollback).
- **A maintenance switch** (`arugula-control maintenance on|off`): chat and
  Cloud answer 503 with `Retry-After` for a few minutes while terminals and
  the relay keep working.
- **Every route has a process**, listed in `crates/control/routes.toml` and
  checked by a test; every table says which process holds it in
  `tables.toml`.
- **The platform's tables are built from numbered migrations**, which adopt
  an existing database (any older release's) in place.

## Clients

- **The daemon's `cloud` tools, the CLI and the page wait out a
  maintenance window** (up to five minutes) instead of failing, and the
  page says "Chat and Cloud are briefly down for maintenance" while one is
  on. Chat's live stream now reconnects after control comes back, instead
  of staying dead until a reload.
